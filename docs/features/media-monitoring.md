## А. Продуктовая идея

FloodValue получает сообщения о паводках из подключённых источников: СМИ, RSS-лент, API и
доступных сводок. Система:

1. отбирает публикации о потенциально значимых событиях;
2. определяет место и время;
3. объединяет повторы;
4. показывает события на основном интерактивном глобусе.

Аналитик выбирает событие, изучает источники, открывает территорию и сопоставляет
сообщение с подходящими спутниковыми наблюдениями. Если актуальных данных мало, событие
становится поводом проверить территорию, а оператор может рассмотреть дополнительную
съёмку. Решение о съёмке оператор принимает в существующем процессе планирования
(`procure`, A/B/C), а не автоматически.

**Ценность — связь «сообщение → территория → наблюдение → решение аналитика»**, а не
агрегатор новостей. Для инфраструктурного оператора (D-001) это ранний сигнал: «где-то
рядом с моими объектами сообщают о воде — есть ли у меня снимок, который это проверяет, и
нужно ли его покупать».

**Чем функция не является:**

- это не обещание обнаруживать все паводки в мире: охват ограничен подключёнными
  источниками и их языками;
- это не официальная система экстренного оповещения: сообщения не проверены, а задержки
  не гарантированы;
- это не автоматическое управление спутниками и не автоматическая закупка съёмки.

## Б. Пользовательский сценарий

1. **Обнаружение.** Фоновая задача по расписанию опрашивает источник и получает новую
   публикацию. Публикация, которая уже обрабатывалась, пропускается.
2. **Относится ли к паводку.** Сначала дешёвый фильтр кода (ключевые слова, язык,
   рубрика источника), затем классификация моделью по фиксированной схеме.
3. **Извлечение.** Из текста извлекаются упомянутые топонимы (строками), время события,
   тип сообщения (раздел Г) и краткая суть. Координаты по названию выдаёт геокодер,
   а не модель.
4. **Повтор или новое событие.** Сопоставление с уже известными событиями по месту, времени,
   содержанию и первоисточнику (раздел Е).
5. **Событие на глобусе.** Создаётся новое событие или обновляется существующее. Маркер
   или область рисуется с той точностью, которая известна.
6. **Карточка.** Аналитик открывает карточку: что сообщается, где, когда, источники,
   точность места и времени, ограничения, что уже проверено.
7. **Территория и наблюдения.** «Открыть территорию» приближает карту. «Найти наблюдения»
   показывает сцены-кандидаты с причинами совпадения и несовпадения по месту и времени.
8. **Результат проверки.** Аналитик фиксирует один из четырёх результатов (раздел З) и
   комментарий.
9. **Съёмка.** При необходимости участок передаётся на рассмотрение дополнительной
   съёмки через существующий процесс планирования. Решение и бюджет остаются за
   оператором (раздел И).

## В. Предлагаемая архитектура

Всё в этом разделе — **предложение**. Ни одного из компонентов в проекте нет.

```text
Планировщик (по расписанию, на сервере)
  → адаптеры источников (по одному на источник: RSS / API / сводка)
  → сбор и нормализация публикаций (единая запись, хеш содержимого, дедуп по URL)
  → предварительный фильтр (код: язык, ключевые слова, рубрика)
  → извлечение фактов (языковая модель, строгая JSON-схема, валидация кодом)
  → географическое уточнение (геокодер + правила точности; неоднозначное — на уточнение)
  → объединение публикаций в события (код: место × время × содержание × первоисточник)
  → хранилище (источники, публикации, события, связи, проверки, журнал запусков)
  → API (чтение событий, действия аналитика)
  → глобус: слой «Сообщения» и карточка события
  → поиск подходящих наблюдений (каталог сцен; анализ — существующий конвейер, вручную)
```

**Работа на сервере независимо от браузера.** Сбор идёт отдельным фоновым процессом, а не
в браузере и не в запросе интерфейса. Интерфейс только читает хранилище и записывает
действия аналитика.

**Периодичность настраивается** для каждого источника (`poll_interval`). Начальное
допущение для обсуждения — **15 минут**. Это не гарантированная скорость обнаружения:
фактическая задержка складывается из задержки публикации у источника, интервала опроса,
обработки и доступности источника. Её нужно измерять (план, этап 9).

**Разделение ответственности:**

| Делает обычный код | Делает языковая модель | Модели запрещено |
|---|---|---|
| Расписание, повторы запросов, лимиты, контроль затрат | Ответ «относится ли текст к паводку» с уверенностью | Выдумывать или «уточнять» координаты: координаты даёт только геокодер или источник |
| Нормализация, хеши, дедуп по URL и содержимому | Извлечение топонимов строками, времени, типа сообщения и сути в заданную схему | Запускать заказы, менять бюджет, зоны, план съёмки |
| Геокодирование, уровень точности, правила неоднозначности | Короткая нейтральная сводка для карточки | Менять p, маску, порог, метрики, EL, A/B/C, объекты |
| Объединение в события, состояния, журнал | — | Выполнять инструкции из текста статьи. Инструменты у модели отсутствуют |
| Проверка ответа модели по схеме; невалидное → «на ручную проверку» | — | Сама решать, что событие подтверждено |

**Размещение в коде (предложение, согласуется в этапе 2 плана).** Новый модуль
`src/floodvalue/media/` с правилами импортов проекта: только `floodvalue.contracts` и
`floodvalue.paths`, без импорта внутренностей `model`, `calibration`, `assets`,
`procurement`, `export`. Запуск — `python -m floodvalue.media …`, отдельно от `make all`.
`make all` и `make validate` должны давать прежний результат. Тест-«файрвол» по образцу
`tests/context/test_firewall.py` проверяет, что модель и расчёты не читают `media`.

**Инфраструктурные зависимости (в проекте их нет, каждую нужно решить отдельно):**

- постоянно работающий процесс или планировщик (варианты: systemd timer, cron, планировщик
  внутри процесса) — где он работает после хакатона, неизвестно;
- хранилище: для MVP предлагается один файл SQLite вне git (`FLOODVALUE_OUTPUT_DIR` или
  отдельная переменная); переход на серверную БД — позже;
- HTTP API: если глобус войдёт в `main` в виде PR #120, логично расширить его FastAPI.
  Если войдёт Streamlit (D-034), нужен отдельный лёгкий API или чтение хранилища напрямую;
- доступ к языковой модели: провайдер, ключ, бюджет;
- новые Python-зависимости — только через `uv.lock`, отдельным PR с `reviewer`.

## Г. Логическая модель данных

Логическое описание сущностей, **без миграций и без выбора СУБД**. Имена полей —
предложение.

**Источник (`source`)**: `source_id`, `name`, `kind` (rss / api / bulletin / citizen —
последний в будущем, раздел К), `url`, `language`, `region_scope`, `poll_interval`,
`enabled`, `terms_status` (checked / требует проверки), `attribution`,
`content_storage_policy` (что разрешено хранить: только ссылку и заголовок или текст),
`last_success_at`, `last_error_at`, `last_error`.

**Публикация (`publication`)**: `publication_id`, `source_id`, `url` (канонический),
`title`, `language`, `published_at` (время публикации по источнику), `fetched_at` (время
получения системой), `content_hash`, `original_source_hint` (на кого ссылается
перепечатка), `text_excerpt` — только если разрешено `content_storage_policy`,
`relevance` (результат фильтра и модели), `extraction` (извлечённые сведения по схеме:
топонимы-строки, время события, тип сообщения, суть), `extraction_confidence`,
`extraction_status` (ok / invalid / needs_review), `is_demo`.

**Событие (`event`)**: `event_id`, `place_label`, `geometry` (точка, полигон области или
пусто), `geo_precision` (point / locality / district / region / country / unknown),
`geo_status` (resolved / ambiguous / missing), `event_time_start`, `event_time_end`,
`time_precision` (hour / day / several_days / unknown), `report_type` (ниже),
`first_detected_at` (время обнаружения системой), `updated_at`, `review_state` (ниже),
`verification_result` (раздел З), `independent_origin_count`, `is_demo`, `is_replay`,
`history` (журнал изменений: кто или что изменило, когда, что было и что стало).

**Связь публикации с событием (`event_publication`)**: `event_id`, `publication_id`,
`link_kind` (auto / manual_merge / manual_split), `linked_at`, `linked_by`
(`system` или аналитик), `is_original` (первоисточник или перепечатка).

**Сопоставление с наблюдением (`observation_match`)**: `event_id`, `observation_ref`
(например `chip_id` из `source_manifest_s1.json` или id из внешнего каталога),
`catalog`, `observation_at`, `footprint`, `spatial_relation` (covers / intersects /
nearby / none), `time_offset` (наблюдение до или после события и на сколько),
`suitability` (suitable / too_early / too_late / partial_cover / unusable) с текстовой
причиной, `analysis_run_id` (комплект `outputs/<run_id>/`, если анализ запускался).

**Результат проверки оператором (`review`)**: `event_id`, `reviewer`, `reviewed_at`,
`verification_result`, `basis` (какие наблюдения и источники смотрели), `comment`,
`follow_up` (none / needs_imagery / merge / split / dismiss).

**Запуск источника (`source_run`)**: `run_id`, `source_id`, `started_at`, `finished_at`,
`status` (ok / partial / failed / skipped_rate_limit), `http_status`, `items_seen`,
`items_new`, `items_relevant`, `error`, `llm_calls`, `llm_cost_estimate`.

### Три времени — не смешивать

| Время | Поле | Откуда |
|---|---|---|
| Время события | `event_time_start`/`end` + `time_precision` | из текста; может быть неизвестно |
| Время публикации | `publication.published_at` | из источника |
| Время обнаружения системой | `publication.fetched_at`, `event.first_detected_at` | часы сервера |

### Тип сообщения (`report_type`)

`occurred` (сообщение о произошедшем событии), `forecast` (прогноз), `warning`
(предупреждение), `negation` (отрицательное сообщение: «подтопления нет», «вода ушла»),
`historical` (исторический материал: годовщина, обзор прошлых паводков), `unclear`.

`forecast` и `warning` не показываются как произошедшее затопление. `negation`
прикрепляется к событию как публикация, но не удаляет его и само по себе не меняет
результат проверки. `historical` по умолчанию на глобусе скрыт.

### Состояние проверки события (`review_state`)

`new` → `needs_geo` (место неоднозначно или отсутствует) → `ready` → `under_review` →
`reviewed`. Помимо этого — `merged_into`, `split`, `dismissed` (с причиной).

### Три разные уверенности — не смешивать

1. **Качество извлечения** (`extraction_confidence`): насколько надёжно из текста
   извлечены место, время и тип. Свойство конвейера.
2. **Достоверность сообщения**: верно ли то, что сообщается. Зависит от источника,
   числа **независимых** первоисточников и проверки аналитиком. Числом, выдуманным
   моделью, не выражается.
3. **Вероятность воды p** из спутниковой модели FloodValue — свойство пикселя конкретной
   сцены. Она появляется, только если аналитик запустил анализ подходящего наблюдения.
   В событие попадает ссылкой на комплект, а не копией.

## Д. Источники и зависимости

**Ни один источник не подключён.** Ниже — кандидаты для исследования, а не обязательный
набор для MVP. Лимиты, условия, лицензии и цены здесь сознательно не указаны: **все
требуют проверки** по официальной документации на дату подключения.

| Кандидат | Зачем | Что проверить |
|---|---|---|
| RSS / API выбранных изданий (региональные СМИ целевого региона) | Первичные сообщения на местном языке | Наличие RSS или API, условия, атрибуция, право хранить текст — требует проверки |
| GDELT (gdeltproject.org) | Широкий поток новостных записей с геопривязкой | Формат, частота обновления, точность геопривязки, условия — требует проверки |
| GDACS (gdacs.org) | Сводки и оповещения о крупных стихийных бедствиях | Формат лент, охват малых паводков, условия — требует проверки |
| ReliefWeb (reliefweb.int) | Гуманитарные сводки и отчёты | API, ключ или идентификатор приложения, лимиты, условия — требует проверки |
| Геокодер (например Nominatim на данных OSM, nominatim.org, или коммерческий) | Топоним → координаты и уровень точности | Политика использования, лимиты, допустимость кеширования, атрибуция — требует проверки |
| Каталог спутниковых наблюдений (например Copernicus Data Space Ecosystem, dataspace.copernicus.eu) | Поиск сцен S1 по месту и времени | API каталога, учётная запись, лимиты, задержка появления сцен — требует проверки |

**Начать с ограниченного перечня:** 1 новостной источник и 1 сводка, один регион и один-два
языка (выбор — этап 1 плана).

**Перед каждым подключением проверить и записать в карточку источника:** доступность,
формат, условия использования, атрибуцию, нужен ли ключ, лимиты, стоимость, можно ли
хранить контент и в каком объёме. Источник, условия которого не проверены, остаётся
`enabled=false`.

**В репозиторий не попадают:** секреты и реальные ключи (только переменные окружения и
`.env.example` без значений), полные тексты чужих публикаций без установленного
основания. По умолчанию хранятся ссылка, заголовок и извлечённые сведения. База событий
лежит вне git, как `data/` и `outputs/`.

## Е. Дедупликация и география

**Одна публикация — не обязательно новое событие. Десять перепечаток — не десять
независимых подтверждений.**

Уровни объединения:

1. **Одна и та же публикация**: канонический URL и `content_hash` → повторно не
   обрабатывается.
2. **Перепечатка**: высокая близость текста или явная ссылка на первоисточник →
   связывается с событием с `is_original=false`. `independent_origin_count` не растёт.
3. **Та же ситуация, другой текст**: совпадение места (пересечение геометрий с учётом
   точности), времени (пересечение интервалов с учётом `time_precision`) и сути →
   кандидат на объединение. При высокой уверенности объединяется автоматически, при
   средней — предлагается аналитику.
4. **Сомнение** → два отдельных события и пометка «возможный дубль», а не молчаливое
   слияние.

Аналитик вручную **объединяет** и **разделяет** события. Операция записывается в
`history` и `event_publication.link_kind`, автоматический пересчёт её не отменяет.

**Правила географии:**

- маркер-точка — только при `geo_precision=point` или `locality`. Для района или области
  рисуется контур или полупрозрачная область, а не булавка в центре;
- уровень точности хранится и показывается в карточке;
- неоднозначный топоним (несколько населённых пунктов с одним названием, нет контекста
  региона) → `geo_status=ambiguous`, `review_state=needs_geo`, список вариантов для
  аналитика. Произвольный выбор запрещён;
- координаты отсутствуют → `geometry` пусто, `geo_status=missing`. **Никаких [0, 0]** и
  никаких «центров страны» вместо неизвестного;
- GeoJSON — WGS 84, порядок [долгота, широта], как во всём проекте.

## Ж. Интеграция с глобусом

Зависит от того, какой интерфейс окажется в `main` (сейчас там интерфейса нет, см.
раздел 0). Концепция описана для глобуса из PR #120.

**Отдельный слой «Сообщения»**, включается и выключается как остальные слои. По
умолчанию он не закрывает S1, p, маску, объекты и зоны: маркеры небольшие,
полупрозрачные, области без заливки поверх растров.

**Карточка события** — боковая панель в существующем тёмном минималистичном стиле, не
новый dashboard и не модальное окно как обязательная точка входа. Содержит:

- что сообщается: тип сообщения, суть, пометка «прогноз / предупреждение», если это они;
- где: название, уровень точности места, геометрия;
- когда: время события и его точность, время первой публикации, время обнаружения;
- источники: список со ссылками и атрибуцией, первоисточник и перепечатки, число
  независимых первоисточников;
- что уже проверено: результат проверки, наблюдения, кто и когда проверял;
- ограничения: «сообщение СМИ не проверено», «место определено до района» и т. п.;
- пометки `ДЕМО` / `REPLAY`, если применимо.

**Фильтры:** период (время события или публикации), тип сообщения, состояние проверки,
точность места.

**Действия:** «Посмотреть источники», «Открыть территорию», «Найти наблюдения»,
«Отправить на проверку».

**Без тревожного шума:** никаких мигающих и пульсирующих маркеров. Новые события
выделяются спокойно, например счётчиком «новых с последнего визита». Близкие события при
отдалении группируются в кластеры. При `prefers-reduced-motion` анимации нет, как в #120.

## З. Проверка по спутниковым данным

Этапы разделены, и каждый — отдельный шаг, а не одна кнопка «подтвердить»:

1. **Найти запись в каталоге** — есть ли наблюдение, которое покрывает территорию в
   подходящее время.
2. **Получить данные** — скачать сцену. Сейчас это только локальные чипы Sen1Floods11.
3. **Подготовить** — привести к формату метода (S1 VV/VH в dB, сетка чипа).
4. **Выполнить анализ** — существующий конвейер (`predict`, при необходимости `make all`)
   даёт p и маску. Мониторинг вызывает его как внешнюю команду и не меняет.
5. **Интерпретировать** — аналитик сопоставляет результат с сообщением.

**Правила интерпретации:**

- найденный снимок ещё не подтверждает сообщение;
- совпадать должны территория (покрытие, а не соседство), время (наблюдение в окне
  события) и пригодность (не старая сцена, не частичное покрытие);
- старый снимок не опровергает новое сообщение;
- вода на одном снимке не доказывает резкий подъём уровня: для вывода об изменении нужны
  сопоставимые наблюдения «до» и «после» (один сенсор, режим и геометрия съёмки). Кроме
  того, модель проекта даёт **карту воды**, а не «временное затопление» (D-007): постоянная
  вода не исключена;
- отсутствие снимка — не отрицательный результат.

**Результаты проверки (`verification_result`):**

| Значение | Когда |
|---|---|
| `not_checked` — не проверено | по умолчанию |
| `consistent` — наблюдения согласуются с сообщением | подходящее наблюдение есть, и аналитик видит воду там и тогда, где сообщается |
| `discrepancy` — есть расхождение | подходящее наблюдение есть, но картина не согласуется. Это не «опровергнуто»: причиной может быть время, растительность или ограничения SAR |
| `insufficient_data` — недостаточно подходящих данных | нет наблюдения нужного места и времени, или оно непригодно |

**Честно о текущем каталоге.** Локальный каталог — чипы Sen1Floods11 событий 2016–2019.
Для сегодняшних публикаций результат почти всегда будет `insufficient_data`. Это
правильное поведение, а не сбой.

**Автоматическая обработка новых спутниковых сцен** — поиск во внешнем каталоге,
скачивание, подготовка произвольной сцены вне формата чипа 512×512 и запуск анализа по
расписанию — **отдельный этап после MVP**. В обещание новостного MVP она не входит.

## И. Ограничения и безопасность

**Новости автоматически не могут:**

- менять вероятность воды p, маску, порог;
- менять независимую оценку качества модели (метрики, журнал test);
- перемещать учебные объекты портфеля;
- изменять ожидаемый ущерб EL;
- запускать платную закупку;
- заменять обязательный сценарий A/B/C.

Новость может стать **поводом для проверки** или, позже, **предложением кандидатной
зоны**. Такая зона проходит все существующие ограничения: Polygon без дыр, ≥ 1 км² до
округления, цена по ПП 840 со сценарной ставкой, охват только по `data_role=event_observation`
и `available_at ≤ decision_deadline`. В план она попадает только решением оператора.
Добавление в `candidate_orders.geojson` источника «из сообщения» — изменение контракта,
отдельный PR с перечнем потребителей и `reviewer` (правило проекта). В MVP этого нет:
«Отправить на проверку» только записывает `review.follow_up=needs_imagery`.

**Сегодняшние публикации не связываются с исторической сценой** только потому, что
совпали координаты. Сопоставление всегда учитывает время (раздел З).

**Replay и демо.** Для демонстрации на исторических данных используется отдельно
помеченный replay-сценарий: тексты сообщений **пишет команда** (вымышленные, `is_demo=true`)
или берутся из разрешённых источников с `is_replay=true`, с привязкой к историческому
событию набора. Правила:

- replay-данные не попадают в независимую проверку модели и не влияют на метрики;
- test запечатан: replay не читает метки test-чипов и не использует test-чипы до
  `eval-test` замороженной конфигурации (CLAUDE.md, D-010, D-033). Для демо до заморозки —
  validation-чип `Sri-Lanka_713926`;
- в интерфейсе replay и демо всегда подписаны.

**Тексты публикаций — недоверенные входные данные:**

- инструкции внутри статьи не являются командами ни для модели извлечения, ни для
  ИИ-агента разработки. У модели извлечения нет инструментов;
- ответ модели проверяется по строгой схеме (pydantic, как контракты проекта).
  Невалидный ответ → `extraction_status=invalid`, на ручную проверку;
- текст отображается безопасно: экранирование, без исполнения HTML и скриптов, ссылки с
  `rel="noopener noreferrer"`.

**Надёжность и затраты:**

- повторы запросов с нарастающей паузой, таймауты, ограничение частоты на источник;
- лимит вызовов модели и оценка затрат на запуск и на сутки. Превышение → источник
  ставится на паузу, а не молча продолжает;
- в интерфейсе видно время последней успешной проверки каждого источника. «Нет новых
  событий» и «источник недоступен» — разные состояния.

## К. Связь с сообщениями очевидцев

Дальнейшее расширение (промпт `docs/prompts/media-citizen-reports-prompt.md`, issue
#156): публичная форма очевидцев становится ещё одним источником (`source.kind=citizen`)
**того же контура событий**. СМИ и сообщения людей используют общую логику географии,
времени, объединения, проверки и связи с наблюдениями. Отдельного второго реестра нет.

**Публичная форма не входит в обязательный MVP мониторинга СМИ.** Перед её публичным
запуском нужно отдельно проверить условия: правовые основания и порядок обработки
персональных данных (контакты, геолокация, фото), модерацию, защиту от спама и
злоупотреблений, хранение и удаление обращений. Это решение принимает человек, а не
агент.
