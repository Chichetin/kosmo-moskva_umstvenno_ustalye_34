## Как здесь выигрывают

20 критериев по 0–5, все равного веса: технические 60 (данные, baseline, основной
метод, сравнение, итоговая карта и порог, split без утечки, перенос, эксперимент,
надёжность вероятностей, неопределённость, повторный запуск, обязательные файлы),

допущения, интерфейс, границы прототипа).

- **Провал любого пункта стоит столько же, сколько провал модели.** Модель — 1 пункт
  из 20 (№ 3). Ширина и честность важнее лишних IoU: сначала каждый пункт на 3, потом
  добор до 5.
- **Треть баллов — дисциплина, а не ум:** split без утечки (6), повторный запуск (11),
  обязательные файлы (12), ПП 840 и допущения (18), границы прототипа (20). Их дают
  валидатор, журнал test, README из чистого клона, сценарные пометки.
- **Экономика — чистая арифметика с контрольными примерами в постановке** (13, 15–17):
  тесты на 1 000 000 руб. EL, 1 703,46 / 946,37 / 567,82 руб., 0,9996 км², границу 90
  дней пишутся до кода.
- **Честность — это баллы:** «карта воды», а не «временное затопление»; `scenario`, а
  не «тариф»; B сверх бюджета — контрфактическая; без новых наблюдений
  неопределённость не снижается; прокси-ошибка ≠ фактические потери.
- **Жюри запускает само**: inference на другом официальном чипе, смена бюджета, код
  обучения. Всё, что не запускается из README в чистом клоне, — ноль.

## Команда и интеграция

Пять равноправных участников, у каждого своя сессия Claude Code. Координатора среди
людей нет. Баллы приносит только то, что соединилось в зелёном `main`.

- **Задачи — GitHub Issues.** Взять = назначить себя assignee (`gh issue edit <N>
  --add-assignee @me`). Метка `area:<модуль>`, в теле «Зависит от #…», критерий и
  команда приёмки. Не брать issue с `area:`, на которой уже есть assignee в работе
  (SessionStart-хук показывает занятые). Карта владения каталогами —
  `docs/project-structure.md`.
- **Контракты — единственная точка стыковки** (`docs/contracts.md`,
  `src/floodvalue/contracts/`). Модули общаются файлами по контракту, не импортом
  внутренностей друг друга. Изменение контракта — отдельный PR с перечнем
  потребителей; merge после вердикта `reviewer`, проверившего каждого.
- **Валидатор 12 файлов (`make validate`) — это критерий 12** и гоняется в каждом PR.
- **Split замораживается один раз** (`splits/`, хеш в `docs/decisions.md`), дальше —
  только отдельный PR с `reviewer` + `jury` + строка в `decisions.md`.
- **Test запечатан.** Никакой код, кроме `make eval-test` для замороженной
  конфигурации, test-чипы не читает. **До заморозки сквозной путь и интерфейс гоняются
  на чипе из validation** (`Sri-Lanka_713926`); демо-чип из test (`Spain_7370579`)
  подставляется после заморозки, его метки читает только `eval-test` (включая прокси-проверку). Каждый запуск — строка в
  `docs/verification/test-log.md` (commit, хеш конфигурации). Повторная настройка
  после просмотра test — новый эксперимент с новым test.
- **Спор решает validation**, не голосование: PR в метод, порог, калибровку,
  постобработку прикладывает таблицу «было → стало» на validation.
- **`main` всегда зелёный.** Перед push: `git fetch --prune && git merge origin/main`,
  полный прогон. Незаконченное вливается неподключённым, а не копится в ветке.
  Сломал `main` — чинишь раньше своей задачи.
- **Общие документы** (`decisions.md`, `tz-compliance.md`, `questions-for-organizers.md`)
  каждый дописывает в своём PR; при конфликте сохраняются обе стороны. Номер `D-…` —
  следующий за последним в `origin/main`; коллизию номеров чинит тот, кто вливает вторым.

## Агент аппрувит сам — через субагентов

Решение по реализации, трактовке условий, методу, порогу, формату, контракту агент не
несёт людям: формулирует → отдаёт свежему субагенту (`reviewer` в режиме «решение» или
скептику, контекст — только решение/diff и условия) → при «принять» пишет `D-…` и идёт
дальше; при «отклонить» исправляет; два отклонения подряд — `jury` как арбитр. PR
вливается после вердикта `reviewer` «merge» и зелёного прогона, без ожидания людей.

К человеку — **только**: учётные данные и доступы (GitHub, GitVerse, Colab),
физические действия, вопросы к организаторам (пишутся в
`docs/questions-for-organizers.md` с рекомендуемой трактовкой и влиянием на баллы;
работа продолжается по рекомендуемой), сокращение объёма обязательных результатов.

**Субагентов не экономим.** `reviewer` — на каждый PR; параллельные `builder` — на
независимые issues; `evaluator` — после каждого изменения метода, порога, калибровки
или экономики; `jury` — перед каждой вехой; скептик — на каждое спорное решение.
`opus` — где нужно суждение (метод, калибровка, неопределённость, экономика, ревью,
jury), `sonnet` — механика (прогоны, README, проход интерфейса). Роли — `docs/agents.md`.

## Модель данных и форматы

- Чип: `EVENT_CHIPID` (например `Spain_7370579`), слои `S1Hand` (2 канала VV/VH,
  float32, dB, nodata = NaN), `LabelHand` (int16: −1 невалидно, 0 не вода, 1 вода).
  EPSG:4326, шаг ≈ 8,983e-05°. Подробно — `docs/data.md`.
- `flood_probability.tif` — Float32, p ∈ [0, 1], nodata −9999; `flood_mask.tif` —
  UInt8, 1/0, nodata 255; та же сетка, что у S1-чипа; mask = 1 ⇔ p ≥ threshold из
  `run_metadata.json`.
- Интерфейс «метод → p-растр»: функция берёт массив S1 (2, H, W) в dB с NaN и
  возвращает p (H, W) float32 с NaN там, где нет данных (`docs/contracts.md`).
- GeoJSON — WGS 84, порядок **[долгота, широта]**; площадь — в EPSG:6933
  (`always_xy=True`), км² = м² / 1e6.
- CSV — UTF-8, запятая, десятичная точка; пусто вместо NaN/Inf, не ноль.
- Нормативные коэффициенты — `configs/pricing.yaml` с редакцией и датой проверки; в
  коде — только формула.
- Схемы 12 файлов — pydantic-модели в `src/floodvalue/contracts/` (D-004).

## Известные ловушки материалов

- **S1 уже в dB** — повторно не логарифмировать. VV встречается до +25 dB — клиппинг.
  Nodata в S1 — NaN (тег `nodata=nan`); у `LabelHand` −1 не объявлен как nodata. Под NaN
  в S1 метка бывает 0/1, а не −1 — маска валидности = S1 конечен **и** метка ≠ −1.
  `nan_to_num` превращает NaN в «яркий сухой» пиксель.
- Шаг пикселя у S1 и метки расходится на ~1e-17° — сравнивать сетки через `allclose`,
  не `==`.
- Авторский split Sen1Floods11 случаен по чипам: все события, кроме Bolivia, в train,
  valid и test одновременно → утечка через соседние чипы. Split — по событиям.
- 5 чипов Ghana целиком −1, 38 чипов > 50 % −1, 52 без воды — учитывать в метриках.
- `LabelHand` — вся вода, не «временное затопление». JRC-слой набора, вероятно,
  собран по данным до 2018+ — для событий 2016–2018 это информация из будущего.
  Пока не доказано иное — «карта воды».
- **EPSG:4326 — порядок осей «широта, долгота», GeoJSON — «долгота, широта».**
- **Площадь не в градусах**: пиксель ≈ 10 м × 10 м·cos(широты); чип 20–26 км², не
  26,2144 км² везде.
- **0,9996 км² — не 1 км²**: минимум проверяется до округления.
- **p — из растра, не из маски**: объект ниже порога не обнуляется.
- **Ровно 90 дней → Т = 1** (operational), не 0,6.
- **Латинская R в формуле скидки — разрешение (`resolution_m`)**, кириллическая Р —
  коэффициент скидки в цене. S в км², r в метрах; не переводить S в м².
- Скидка Р пересчитывается по **всей корзине** группы; нельзя суммировать заранее
  посчитанные цены одиночных зон.
- ROUND_HALF_UP (`decimal`), а не банковское округление Python `round`.
- `polygon.covers(point)`, не `contains` — граница считается покрытой.
- `rank` — 1 у максимального EL, при равенстве — по `asset_id`; у `partial`/`no_data` — пусто.
- Охват зонами считается только по `data_role=event_observation` и `available_at ≤
  decision_deadline`; архивный/контекстный снимок не наблюдает текущую воду.
- Доля воды в train (≈ 8 %) вдвое ниже, чем в validation/test (15–18 %) — без калибровки
  на validation вероятности на test занижены.

## Код и архитектура

- Python 3.12, uv (`uv.lock` — единственный источник версий). Пакет
  `src/floodvalue/`: `data`, `baseline`, `model` (подкаталоги `pixel`, `unet`, модуль
  `eval_test` — `area:model-pixel`/`model-unet`/`eval`), `calibration`, `assets`,
  `procurement`, `export`, `app` — без взаимных внутренних импортов; общее — только
  `floodvalue.contracts` и `floodvalue.paths`.
- **Одна команда на этап и одна на всё** (`make <этап>` = `python -m floodvalue
  <этап>`): `data`, `split`, `baseline`, `train`, `calibrate`, `predict CHIP=…`,
  `assets`, `procure BUDGET=…`, `export`, `validate`, `app`, `eval-test`; `make all` —
  сквозной путь на готовых весах.
- Экономика, цена, геометрия, метрики — чистые функции без ввода-вывода, с тестами.
- Обучение — тот же код локально или в Colab (ноутбук-обёртка в `notebooks/` только
  вызывает `python -m floodvalue train`). Веса — `models/`, через LFS, с sha256 в
  `run_metadata.json`. CPU-inference одного чипа без GPU.
- Данные вне git: `FLOODVALUE_DATA_DIR` (по умолчанию `data/`), результаты —
  `FLOODVALUE_OUTPUT_DIR` (`outputs/`).
- Плоский код: никаких фабрик, реестров и конфиг-движков «на будущее». Идентификаторы и
  комментарии — английские; интерфейс и документация — русские. Правки только в зоне
  задачи.

```bash
make setup        # uv sync --frozen + git-хук стража данных
make test         # pytest
make check        # pytest + test-hooks + validate — перед каждым push
```

## Тесты и доказательство

- Новая логика → тест в том же коммите. Багфикс начинается с воспроизводящего теста.
- Обязательные тесты: контрольная арифметика постановки; валидатор на эталонном
  комплекте и на сломанных (NaN, дыра, 0,9996 км², дубль `asset_id`, маска ≠ порогу);
  «бюджет меняется — p, маска, порог не меняются»; round-trip GeoJSON [lon, lat].
- **Нет команды и вывода — нет «работает».** Ни в чате, ни в README, ни в PR.
- Числа метрик — только из `docs/verification/` со ссылкой на файл.
- Stop-хук `check-tests.sh` не даёт закончить ход с красным pytest; пока тестов нет —
  молчит.

## Принципы Карпаты — адаптация

1. **Become one with the data.** Открыть чип, посмотреть VV/VH, метку, NaN до кода модели.
2. **Сквозной путь раньше качества.** Baseline-порог как временный основной метод
   (p = сигмоида от расстояния до порога) проходит всю цепочку до 12 файлов и UI.
3. **Тупой бейзлайн прежде умного.** Otsu/порог VH, потом логистическая регрессия /
   бустинг по пикселям, потом компактный U-Net — каждый шаг оправдан validation.
4. **Переобучить один батч** — проверка проводки, не качества.
5. **Визуализировать всё**: p, маску, ошибки, неопределённость — картинкой в
   `docs/verification/`.
6. **Не доверять своим числам**: одна и та же маска валидных пикселей, test запечатан.
7. **Журнал решений.** Решение — `D-…` в `docs/decisions.md`: что / почему / что отвергли.

## Git кратко

Полностью — `GIT.md`. Задача → свой worktree `.claude/worktrees/<issue>-<тема>`, ветка
`worktree-<issue>-<тема>`. PR в `main` закрывает issue (`Closes #N`). Коммит и push
ветки — без запроса разрешения после проверенного шага; `git add <пути>`; без
трейлеров соавторства ИИ; force-push, rebase, amend, `reset --hard`, `add -A`, push в
`main` запрещены (`.claude/settings.json`).
